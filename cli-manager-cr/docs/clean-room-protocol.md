# Clean-room 절차

목적: `cli-manager`(BrightTerm v1.1.0 이식물)와 별개의 **독자 저작물**을 만든다. 구현자가 원본 코드의 표현을 접하지 않도록 역할을 나눈다.

> 이 문서는 개발 절차이며 법률 자문이 아니다. 법적 효력은 보장되지 않으므로 배포·고지 정리 전에 전문가 확인을 받는다.

## 1. 역할

| 역할 | 하는 일 | 접근 | 금지 |
|---|---|---|---|
| **명세 작성자** | 기존 앱을 실행·관찰하고 코드를 읽어 `spec/` 작성, `QUESTIONS.md` 답변, 대조 결과 반영 | 기존 앱, `../cli-manager/**`, `spec/` | 이 폴더의 구현 코드 작성 |
| **구현자** | `spec/` 만 보고 구현·테스트 | `spec/**`, 이 폴더 코드, 공개 라이브러리 문서 | `../cli-manager/**`, BrightTerm 저장소·태그, 기존 빌드 산출물 열람 |
| **검수자** | 두 결과를 앱 단위로 나란히 실행해 차이를 관찰·기록 | 실행 파일, `spec/`, 결과물 | 구현 코드 베끼기 위해 기존 코드 열기 |

한 세션/에이전트는 한 역할만 맡는다. 같은 세션이 명세 작성자에서 구현자로 바뀌지 않는다.

## 2. 명세에 쓰는 것 / 쓰지 않는 것

| 쓴다 | 쓰지 않는다 |
|---|---|
| 화면 구성, 사용자가 보는 문구, 동작 순서, 조건 분기, 경계값, 오류 메시지, 단축키 | 코드 조각, 함수·변수·타입·CSS 클래스·파일/모듈 구조 이름 |
| 수치(크기·간격·색상 값·시간·한도) — 관찰 가능한 사실 | 알고리즘을 코드 문장처럼 옮긴 의사코드 |
| 파일 형식(JSON 필드, 암호 매개변수) — 호환에 필요한 사실 | 내부 상태 관리 구조, 컴포넌트 분할 |
| 외부에 관찰되는 IPC 채널·페이로드 계약 | 원본의 테스트 코드 |

모호하거나 관찰로 알 수 없는 것은 "미정"으로 두고 구현자가 질문하게 한다.

## 3. 절차

1. 명세 작성자가 `spec/` 문서를 쓰고 `spec/README.md` 의 상태를 `ready` 로 바꾼다.
2. 구현자가 새 세션에서 이 폴더로 시작한다. 시작 직후 `CLAUDE.md` 의 clean-room 규칙을 확인한다.
3. 구현 중 막히면 `spec/QUESTIONS.md` 에 `Q<번호>` 로 적고 해당 부분은 건너뛰거나 멈춘다.
4. 명세 작성자가 답을 `spec/` 본문에 반영하고 질문을 `answered` 로 닫는다 (답은 질문 칸이 아니라 명세 본문에).
5. 화면 단위로 기존 앱과 나란히 실행해 차이를 관찰한다. 차이는 명세 수정 → 구현 수정 순서.
6. 위반이 있었다면 `docs/clean-room-log.md` 에 일자·내용·조치를 적는다.

## 4. 점검 체크리스트 (배포 전)

- [ ] 구현 폴더에 `cli-manager` 에서 복사된 파일·코드가 없다 (파일 해시·문자열 유사도 점검)
- [ ] 의존성에 기존 코드·BrightTerm 이 없다
- [ ] `docs/clean-room-log.md` 의 위반이 모두 조치되었다
- [ ] 명세에 코드 표현이 옮겨지지 않았다 (샘플 검토)
- [ ] `LICENSE`(kai 단독 MIT, D8)·정보 화면 표기를 전문가와 확인했다
