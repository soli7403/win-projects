## 0. 요약

**증상**: SSH 세션을 연결해 둔 채 화면 보호기가 켜졌다가 돌아오면, DariTerm 이 그 세션의 **SSH 로그인 비밀번호**를 다시 묻는다.

**원인**: 화면 보호기가 켜진 동안 두 가지가 같이 일어난다.
1. DariTerm 의 **자동 잠금**이 볼트(계정 저장소)를 잠근다.
2. SSH 연결이 끊겨 **자동 재접속**이 돈다.

재접속은 비밀번호를 **볼트에서만** 다시 읽는다. 그런데 잠긴 볼트에서는 읽을 수 없고, 코드가 이 경우를 "저장된 비밀번호 없음"과 똑같이 처리한다. 그래서 비밀번호 창이 뜬다.

평소 재접속에서 비밀번호를 묻지 않는 것은 비밀번호가 볼트에 저장되어 있고 볼트가 열려 있기 때문이다. 처음 입력한 비밀번호를 세션이 기억했다가 다시 쓰는 기능은 없다.

**두 번째 증상(같은 날 추가 보고)**: 화면 보호기와 상관없이, 세션을 백그라운드에 오래 두기만 해도 암호 창이 뜬다. 이 서버는 입력이 없으면 연결을 스스로 끊는다.

**두 번째 증상의 원인**: 앱은 **서버가 정상적으로 세션을 끝낸 것**과 **네트워크가 끊긴 것**을 구분하지 않는다. 서버의 유휴 자동 로그아웃도 "끊김"으로 보고 2초 뒤 자동 재접속하며, 그때 쓸 비밀번호가 없으면(저장 안 함 또는 볼트 잠김) 암호 창을 띄운다.

**권장 수정**:
- **안 F**: 서버가 정상적으로 세션을 끝냈으면 **자동 재접속하지 않고** "Enter 키를 누르면 다시 연결합니다"만 보여 준다. 네트워크가 끊긴 경우에만 자동 재접속한다.
- **안 E**: 세션이 접속할 때 쓴 계정 정보를 그 세션 메모리에 사본으로 둔다. 볼트가 잠겨 있으면 그 사본으로 **묻지 않고 자동 재접속**한다.
- **안 A**: 사본으로도 안 되는 경우(인증 실패, 호스트 키 확인 필요 등)에는 잠긴 동안 창을 띄우지 않고 **볼트 잠금 해제를 기다렸다가** 다시 시도한다.

## 1. 용어

| 용어 | 뜻 |
|---|---|
| 볼트(vault) | 서버 계정(사용자 이름·비밀번호·개인 키·키 암호)을 암호화해 저장하는 곳. "앱 잠금 비밀번호"로 연다 |
| 볼트 잠금 | 메모리에 있던 볼트 키를 0 으로 덮어써 지운다. 잠긴 동안에는 앱도 저장된 계정을 복호화할 수 없다. 화면에는 잠금 화면이 덮인다 |
| 자동 잠금 | 설정 "자동 잠금 (분)"(0 이면 끔). 20초마다 검사해 조건이 맞으면 볼트를 잠근다. **열린 터미널 세션은 끊지 않고 유지한다** |
| 자동 재접속 | 설정 "연결이 끊기면 다시 연결". 연결된 적이 있는 세션이 끊기면 2·4·8·16·30초 간격으로 다시 접속한다(최대 8회, 시리얼 제외) |
| keepalive | SSH 연결 확인 요청. 기본 30초 간격이고, 연속 4번 실패하면(약 2분) 연결을 끊고 재접속 규칙으로 넘어간다 |
| 다이얼러 | 세션이 접속(재접속 포함)할 때마다 부르는 함수. 매번 서버 설정과 볼트에서 접속 정보를 새로 만든다 |

## 2. 증상 (사용자 보고, 2026-11-17)

1. 서버를 새로 만들고 연결 → 비밀번호 입력 → 연결됨
2. 아무것도 하지 않아 Windows 화면 보호기가 켜짐
3. 화면 보호기를 **Windows 암호**로 해제
4. DariTerm 이 그 세션의 **SSH 로그인 비밀번호**를 다시 물음(앱 잠금 비밀번호가 아님)

사용자는 "재연결이 설정되어 있으면 보통은 비밀번호를 안 묻는 것 같다"고 했다. 이 관찰은 **볼트에 저장된 비밀번호를 읽을 수 있을 때만** 맞다(§3.3).

### 두 번째 증상 (추가 보고, 2026-11-17)

- 화면 보호기와 관계없이, 세션을 **백그라운드에 오래 두기만 해도** SSH 로그인 암호 창이 뜬다.
- 연결된 서버는 **입력이 없으면 자동으로 연결을 끊는다**(서버 쪽 설정).

원인은 §3.6 이다.

### 3.2 문제 지점 코드

볼트에서 계정을 읽는 함수다. "잠김" 오류와 "항목 없음"을 구분하지 않고 둘 다 그냥 돌아간다.

```go
// internal/app/ssh_app.go:126-140
func (pService *Service) applyCredential(tgt *sshconn.Target, szCredentialId string) {
	if szCredentialId == "" {
		return
	}
	body, errGet := pService.pVault.Get(szCredentialId)
	if errGet != nil || body == nil {   // ← 볼트 잠김(ErrLocked)도 여기서 조용히 끝남
		return
	}
	...
	tgt.Password = body.M_szPassword
	...
}
```

	if conn.Asked.Asked && conn.Asked.Save && pService.pVault.Status().M_bUnlocked {

	}
	...
}

### 3.3 세 요인이 겹쳐서 생긴다

| # | 요인 | 설명 | 이번 증상에서의 역할 |
|---|---|---|---|
| ① | 볼트 자동 잠금 | 화면 보호기 동안 유휴 시간, Windows 잠금, 절전 중 하나로 볼트가 잠긴다. 명세상 의도된 동작이다 | 재접속 시점에 볼트가 잠겨 있게 만든다 |
| ② | 연결 끊김 → 자동 재접속 | 화면 보호기 뒤 절전·네트워크 정지 등으로 keepalive 가 실패하거나 서버가 연결을 끊는다 | 비밀번호가 다시 필요한 상황을 만든다 |
| ③ | 잠김을 "비밀번호 없음"으로 처리 | §3.2 의 `applyCredential` | **직접 원인.** "볼트를 열어 달라"가 아니라 "SSH 비밀번호를 넣어라"가 된다 |

함께 확인된 점:
- **재접속 창에서 "저장"을 체크해도 저장되지 않는다.** 볼트가 잠겨 있으면 저장 단계를 조용히 건너뛴다(§3.2 두 번째 코드).
- **점프 서버도 같다.** 점프 서버 계정도 같은 함수로 읽는다(ssh_app.go:108, 115).
- **처음 열기도 같다.** 볼트가 잠긴 상태에서 저장된 서버를 열어도 같은 경로로 비밀번호 창이 뜬다.

### 3.4 화면 보호기와 볼트 잠금(①)의 관계

| 경우 | 볼트 잠금 | 설명 |
|---|---|---|
| 화면 보호기 설정 "다시 시작할 때 로그온 화면 표시" 켬 | 잠김(의도된 동작) | Windows 세션이 실제로 잠긴다. 명세가 "Windows 를 잠그면 볼트도 잠근다"로 정한 동작 |
| 위 옵션 끔 | **잠길 수 있음(추정, 실측 필요)** | 화면 보호기는 별도 데스크톱에서 돌아 `OpenInputDesktop` 이 접근 거부를 돌려줄 수 있다. 그러면 실제 잠금이 아닌데도 잠김으로 판단한다 |
| 자동 잠금 분 ≤ 화면 보호기 대기 시간 | 잠김 | 유휴 조건이 먼저 맞는다 |
| 화면 보호기 뒤 절전 | 잠김 | 절전 추정 조건 |

사용자는 화면 보호기를 **Windows 암호로** 해제했으므로 첫 번째 경우(실제 Windows 잠금)다. 볼트가 잠긴 것 자체는 명세대로다. **고쳐야 할 것은 ③**이다.

### 3.5 끊김(②)의 가능 원인 — 환경 요인

- 화면 보호기 뒤 절전 또는 Modern Standby 로 네트워크가 멈춰 keepalive 가 실패한다. 서버도 응답 없는 클라이언트를 끊는다.
- 네트워크 어댑터의 "전원 절약을 위해 장치를 끌 수 있음" 설정.
- 서버 `ClientAliveInterval`/`ClientAliveCountMax`, 방화벽·NAT 유휴 시한(keepalive 30초면 보통 문제없음).

끊김은 자동 재접속이 처리하므로, 이 계획은 끊김을 막는 것이 아니라 **재접속이 불필요하게 비밀번호를 묻지 않게** 하는 데 초점을 둔다.

### 3.6 두 번째 증상의 원인 — 서버가 끝낸 세션도 "끊김"으로 보고 자동 재접속한다

**문제 지점 코드**

셸이 어떻게 끝났는지(`session.Wait()` 의 결과)를 버린다. 정상 종료인지 연결이 끊긴 것인지가 여기서 사라진다.

```go
// internal/sshconn/shell.go:60-75
	// 셸이 끝나면 출력 파이프를 닫아 Read 가 끝나게 한다.
	go func() {
		_ = session.Wait()        // ← 종료 사유를 버림
		_ = outWriter.Close()
	}()
...
func (pShell *Shell) Read(bBuf []byte) (int, error) {
	nRead, errRead := pShell.outReader.Read(bBuf)
	if errRead != nil {
		return nRead, transport.ErrRemoteClosed   // ← 어떤 끝이든 같은 오류
	}
	return nRead, nil
}
```

세션 쪽은 읽기가 끝나면 이유를 가리지 않고 끊김으로 처리한다.

```go
// internal/session/session.go:243-249
		if errRead != nil {
			szReason := ""
			if !errors.Is(errRead, io.EOF) {
				szReason = errRead.Error()
			}
			pSession.onDisconnected(szReason, iGen)   // ← 정상 종료도 끊김과 같은 길
			return
		}
```

**함께 확인된 점**
- **keepalive 로는 막지 못한다.** 앱이 30초마다 보내는 keepalive 는 연결 확인 신호라 서버 셸은 입력으로 치지 않는다. 방화벽의 유휴 차단은 막아 주지만 셸의 유휴 로그아웃은 그대로 일어난다.
- **사용자가 `exit` 를 쳐도 같은 길이다.** 코드상 셸에서 `exit` 로 나가도 2초 뒤 자동 재접속할 것으로 보인다(실행해서 확인하지는 않았다, §4-6).
- **볼트 상태와 무관하게 생길 수 있다.** 처음 접속 때 비밀번호를 저장하지 않았다면 볼트가 열려 있어도 재접속마다 묻는다. 사용자가 다른 프로그램을 쓰고 있었다면 유휴 시간 조건으로 볼트가 잠기지도 않으므로, 두 번째 증상에서는 "저장 안 함"일 가능성이 높다(§4-3 에서 확인).
- **현재 명세도 이렇게 정한다.** 재접속 규칙은 "한 번 연결됐다가 끊기면 자동 재접속을 시작한다"이고, 서버가 끝낸 경우를 따로 다루지 않는다. 즉 구현 오류가 아니라 명세에 빠진 경우다.

| 3 | 사용자 설정값: 자동 잠금 분, 자동 재접속, 서버에 저장된 계정이 있는지(첫 접속에서 "저장" 체크 여부) | 사용자 확인 | (미확인) |
| 4 | 세션 터미널에 `● 연결 끊김: …`, `● n초 후 자동 재연결합니다…` 줄이 찍혔는지(②가 실제로 일어났는지) | 사용자 확인 | (미확인) |

| 5 | 서버가 세션을 끊을 때 터미널에 찍히는 마지막 줄. `timed out waiting for input: auto-logout` 류이면 셸의 유휴 로그아웃(정상 종료)이고, 아무 문구 없이 끊기면 서버·방화벽이 연결 자체를 끊은 것이다 | 사용자 확인 | (미확인) |
| 6 | 셸에서 `exit` 를 쳤을 때 2초 뒤 자동 재접속하는가(§3.6) | 수동 재현 | (미확인) |
| 7 | 서버가 연결 자체를 끊는 방식(sshd 의 유휴 차단 등)일 때 Go SSH 라이브러리가 "종료 코드 없이 끝남"으로 알려 주는가. 안 F 의 구분 기준이 여기에 달려 있다 | 시험 서버에서 두 방식으로 끊어 보고 `session.Wait()` 결과 기록 | **Go 시험 서버(in-process)로 확인**(`internal/sshconn/shell_exit_test.go`): 종료 코드 0·3, exit-signal → 정상 종료 / 종료 코드 없이 채널 닫기, TCP 끊기, 사용자 Close → 끊김. 실제 OpenSSH sshd 에서는 미확인 |

2번에서 비밀번호 창이 잠금 화면 위에 떠 입력을 받는다면, 그것도 별도 문제로 다룬다.

## 5. 수정 방안

### 안 F (권장) — 서버가 정상적으로 끝낸 세션은 자동 재접속하지 않는다

두 번째 증상(§3.6)의 직접 수정이다.

**동작**
1. SSH 셸이 끝난 방식을 둘로 나눈다.
   - **정상 종료**: 서버가 종료 코드(또는 신호)를 보내고 채널을 닫았다. 유휴 자동 로그아웃, 사용자의 `exit`·`logout`, 관리자의 세션 종료가 여기에 든다.
   - **끊김**: 종료 코드 없이 끝났거나 전송 오류가 났다. 네트워크 단절, keepalive 실패, 절전 복귀가 여기에 든다.
2. **정상 종료면 자동 재접속하지 않는다.** 세션 상태를 "닫힘"으로 두고 터미널에 안내 줄을 출력한다. 예: `● 서버가 세션을 끝냈습니다.` 다음 줄에 기존 문구 `● Enter 키를 누르면 다시 연결합니다.`
3. 끊김이면 지금처럼 자동 재접속한다(안 E·A 의 규칙 적용).
4. Enter 또는 [재연결]로 다시 연결하는 동작은 그대로다.

**변경 위치(예정)**

| 파일 | 변경 |
|---|---|
| `internal/sshconn/shell.go` | `session.Wait()` 결과를 보관한다. 결과가 "오류 없음" 또는 "종료 코드 있음"(`*ssh.ExitError`)이면 정상 종료, "종료 코드 없음"(`*ssh.ExitMissingError`)이나 그 밖의 오류면 끊김. `Read` 가 정상 종료일 때 구분되는 오류를 돌려준다 |
| `internal/transport` (오류 정의) | 정상 종료를 뜻하는 오류 값 추가(예: `ErrRemoteExited`) |
| `internal/session/session.go` 읽기 루프·끊김 처리 | 정상 종료 오류면 재접속을 예약하지 않고 "닫힘" + 안내 줄. 재시도 횟수는 0 으로 |
| `internal/session/messages.go` | 정상 종료 안내 문구 |
| `locales/*.json` (10개 언어) | 문구 추가 |

**영향·회귀 위험**
- 지금은 `exit` 뒤에도 다시 붙던 세션이 닫힌 채로 남는다. 의도한 변화지만 사용자에게는 달라 보인다 → 변경 이력에 적는다.
- **세션 유지(tmux)** 를 켠 서버: 지금은 끊기면 자동 재접속해 tmux 에 다시 붙는다. 정상 종료(예: tmux 에서 빠져나온 뒤 셸이 유휴 로그아웃됨)에서는 자동으로 다시 붙지 않게 된다. 이 경우도 같은 규칙으로 둘지는 §6 Q7.
- **텔넷**: 서버가 연결을 닫는 것과 네트워크 끊김을 종료 코드로 구분할 수 없다. 이번 변경에서는 SSH 만 다루고 텔넷은 지금처럼 둔다(§6 Q7).
- **구분이 틀릴 가능성**: 서버가 연결 자체를 끊는 방식에서 라이브러리가 어떻게 알려 주는지는 §4-7 에서 확인한다. 틀리게 구분되면 자동 재접속이 일어나지 않아야 할 때 일어나거나 그 반대가 된다.

**안 F 만으로 달라지는 것**: 백그라운드에 둔 동안 암호 창이 뜨지 않는다. 돌아와서 Enter 를 눌렀을 때는 지금처럼 암호를 물을 수 있다(저장 안 한 서버). 그것까지 없애는 것이 안 E 다.

### 안 E (권장) — 세션별 계정 사본으로 잠긴 동안에도 자동 재접속

**왜 볼트에서 직접 읽지 않나**: 볼트 잠금은 볼트 키를 메모리에서 지우므로, 잠긴 뒤에는 볼트를 복호화할 수 없다. 그래서 **잠기기 전에 받아 둔 사본**을 쓴다.

**근거(사용자 의견, 2026-11-17)**
- 볼트가 잠겨도 열린 세션은 유지된다. 이미 인증된 셸이 살아 있는 것이 비밀번호 사본보다 훨씬 큰 자산이라, 사본을 두어도 위험이 크게 늘지 않는다.
- 잠금 화면이 덮여 있으면 입력도 출력 확인도 안 되므로, 잠긴 동안 재접속해도 노출되는 것이 없다.

**동작**
1. 다이얼러가 볼트에서 계정을 읽으면 그 값(대상 서버와 점프 서버의 사용자 이름·비밀번호·개인 키·키 암호)을 **그 세션의 메모리**에 사본으로 둔다. 사용자가 창에 직접 입력해 **인증에 성공한** 비밀번호도 저장 여부와 상관없이 같은 사본에 둔다.
2. 재접속할 때:
   - 볼트가 **열려 있으면** 지금처럼 볼트에서 새로 읽고 사본을 갱신한다. 그래야 그사이 바꾼 계정이 반영된다.
   - 볼트가 **잠겨 있으면** 사본으로 채운다.
3. **잠긴 동안에는 어떤 창도 띄우지 않는다.** 비밀번호, 호스트 키 확인, 키 암호, 키보드-인터랙티브가 모두 해당된다. 사본으로 인증에 실패하거나 사본이 없거나 질문이 필요하면 접속을 멈추고 안 A(잠금 해제 대기)로 넘어간다. 잠금 화면 뒤의 창에 자동으로 응답하지 않는다.
4. 세션을 닫으면 사본을 지운다. 문자열은 참조를 끊고, 개인 키 바이트는 0 으로 덮어쓴다.

**변경 위치(예정)**

| 파일 | 변경 |
|---|---|
| `internal/app/ssh_app.go` 다이얼러(`sshDialer`) | 세션마다 하나인 다이얼러에 계정 사본을 둔다. 볼트에서 읽으면 갱신, 잠김이면 사본 적용, 접속 성공 시 입력한 비밀번호로 갱신 |
| `internal/app/ssh_app.go` `applyCredential` | 결과를 "읽음 / 항목 없음 / 잠김" 세 가지로 구분해 돌려준다(안 A 와 공통) |
| `internal/app/ssh_app.go` 질문 창 처리(`askPrompter`) | 볼트가 잠겨 있으면 창을 띄우지 않고 "잠김으로 중단" 오류를 돌려준다 → 안 A |
| `internal/session` | 세션을 닫을 때 다이얼러의 사본 삭제를 부른다 |

**남는 위험과 받아들이는 이유**
- 잠긴 동안에도 평문 비밀번호가 프로세스 메모리에 있어, 크래시 덤프나 페이지 파일에 남을 수 있다. 잠긴 동안 세션을 열어 두는 기존 정책과 같은 수준이다. 같은 사용자 권한으로 프로세스 메모리를 읽을 수 있는 공격자는 이미 열린 세션의 데이터도 읽을 수 있다.
- SSH 라이브러리(`golang.org/x/crypto/ssh`)의 비밀번호 인증은 `string` 을 받으므로 메모리에서 확실히 0 으로 지울 수는 없다(참조를 끊는 데까지만). 지금 접속 경로도 같다.
- Windows DPAPI 로 감싸 둔 볼트 키로 백엔드가 잠긴 볼트를 몰래 여는 방법은 **쓰지 않는다**. 앱 잠금이 의미를 잃는다.

### 안 A (대비책) — 사본으로 안 될 때는 볼트 잠금 해제를 기다린다

**동작**
- 저장된 계정이 있는 서버(또는 점프 서버)인데 볼트가 잠겨 있고 쓸 수 있는 사본이 없거나 사본으로 실패하면, **비밀번호 창을 띄우지 않는다.**
- 세션 상태는 "재접속 중"으로 두고, 터미널에 안내 줄을 출력한다. 예: `● 앱 잠금을 해제하면 다시 연결합니다.`(회색, 10개 언어)
- 볼트가 열리면 기다리던 세션을 **곧바로 재접속**한다. 이 대기는 재시도 횟수(최대 8)에 넣지 않는다.
- 기다리는 중 Enter 나 [재연결]을 누르면 잠금 화면을 보여 준다.
- 처음 열기에도 같은 규칙을 적용한다.
- **볼트를 아예 설정하지 않은 사용자**는 지금처럼 비밀번호를 묻는다(기다려도 열 볼트가 없음).

**변경 위치(예정)**

| 파일 | 변경 |
|---|---|
| `internal/app/ssh_app.go` 접속 정보 만들기·다이얼러 | 대상이나 점프 서버 중 하나라도 "잠김 + 사본 없음"이면 접속하지 않고 전용 오류를 돌려준다 |
| `internal/session/session.go` 접속·실패 처리 | 그 오류면 "볼트 대기"로 둔다. 실패 안내·재시도 예약·횟수 증가 없이 안내 줄만 출력 |
| `internal/session` 세션 관리 | 대기 중인 세션을 다시 접속시키는 진입점(예: `ResumeVaultWaiters`). 재접속 세대 검사는 유지 |
| `internal/app/app.go:59` 볼트 열림/잠김 알림 콜백 | 볼트가 열리면 위 진입점을 부른다 |
| `locales/*.json` (10개 언어) | 안내 문구 추가 |
| 프런트엔드 | 필요하면 대기 상태를 표시한다. 상태 값은 기존 "재접속 중"을 쓰고 메시지로 구분하면 IPC 계약은 바뀌지 않는다 |

**영향·회귀 위험**
- 세션 상태 전이에 새 경로가 생기므로, 재접속 세대·사용자 닫기·재시도 타이머 사이의 경합을 테스트로 막아야 한다.
- 저장 비밀번호가 서버에서 바뀐 경우, 볼트가 열려 있으면 지금처럼 인증 실패 → 비밀번호 창으로 간다.
- 텔넷·시리얼·로컬 세션은 볼트 계정을 쓰지 않으므로 영향이 없다.

### 안 C (보조, 조건부) — 화면 보호기를 Windows 잠금으로 오인하지 않게

- 지금의 판정(`OpenInputDesktop` 접근 거부 = 잠김, `internal/app/lifecycle_windows.go:42-50`)을 **Windows 세션 상태 조회**로 바꾼다. `WTSQuerySessionInformationW(…, WTSSessionInfoEx)` 의 `SessionFlags == WTS_SESSIONSTATE_LOCK` 으로 판정하며, 지금의 20초 검사 구조를 그대로 쓸 수 있다.
  - 대안: `WTSRegisterSessionNotification` 으로 잠금 알림을 받는 방법. 창 메시지 루프에 걸어야 해서 더 복잡하다.
  - Windows 7 이하에는 이 값이 반대로 나오는 알려진 문제가 있으나, 대상(Windows 10/11)에는 해당 없다.
- 효과: "로그온 화면 표시"를 끈 화면 보호기에서는 볼트가 잠기지 않는다. §4-1 실측에서 오인이 확인될 때만 한다.
- 이번 사용자 사례(실제 Windows 잠금)는 안 C 로 해결되지 않는다.

### 안 D (환경, 코드 아님) — 끊김 자체 줄이기

- PC 전원 옵션에서 화면 보호기 뒤 절전 시간과 네트워크 어댑터 전원 관리를 확인한다(`powercfg /requests`, `powercfg /a`).
- 끊기지 않으면 재접속도 없어서 이 증상이 나타나지 않는다. 사용자 안내로만 둔다.

### 검토 후 제외한 안

- **안 B(저장 안 한 입력 비밀번호만 세션 동안 재사용)**: 처음에는 "볼트가 잠기면 지워야 하므로 이 문제에는 효과가 없다"며 별도 기능으로 뺐다. 안 E 의 근거(잠긴 동안 세션을 유지하는 정책과 같은 위험 수준)를 받아들여 **안 E 에 합쳤다**.

### 권장 조합

**안 F + 안 E + 안 A.**
- 안 F: 서버가 끝낸 세션에는 자동으로 다시 붙지 않는다(두 번째 증상).
- 안 E: 네트워크 끊김 뒤의 자동 재접속과 Enter 재접속에서 암호를 묻지 않는다(첫 번째 증상, 저장 안 한 서버).
- 안 A: 사본으로 안 되는 경우만 잠금 해제를 기다린다.

안 C 는 실측 결과에 따라 하고, 안 D 는 사용자 안내다.

**안 E 만 하고 안 F 를 하지 않으면** 서버가 유휴 로그아웃시킨 세션에 앱이 조용히 다시 로그인한다. 서버가 유휴 세션을 끊는 것은 보통 보안 정책이므로, 그 취지와 어긋날 수 있다. 그래서 둘을 함께 적용한다. 서버의 유휴 로그아웃을 피하려고 가짜 입력을 보내는 방법은 같은 이유로 넣지 않는다.

- **자동 잠금(lifecycle §2)**: 20초마다 검사한다. 마지막 입력 후 경과가 설정 분 이상이면 볼트를 잠그고, 열린 세션은 유지한다. Windows 를 잠그거나 절전할 때도 잠근다(설정 도움말과 맞추려는 구현 결정).
- **재접속(session §4)**: 한 번 연결됐다가 끊기면 자동 재접속한다. 처음 접속 실패에는 자동 재접속하지 않는다. 최대 8회까지 시도하고, Enter 나 [재연결]로 즉시 재접속할 수 있다.
- **SSH 인증 순서(protocols §2.2)**: 개인 키 → 에이전트 → 저장된 비밀번호 → 키보드-인터랙티브 → 비밀번호 직접 입력(최대 4번).
- **볼트 잠금(data/vault)**: 메모리의 볼트 키를 0 으로 덮어쓰고 비운다.
